# Repair V2 dashboard health and queue feeds

## Summary

The dashboard keeps Hermes as its readiness source and reads Curator queue counts separately. This prevents a Hermes probe failure from hiding valid Curator counts. Feed failures stay separate, repeated reads are coalesced, and unchanged generated queue files are not rewritten.

## Implementation

- In the V2 VS Code extension, keep Hermes as the readiness source. Read a dedicated Curator `project_queue_snapshot` tool for queue counts, using the same authorized project and MCP session. This snapshot reads only project-scoped SQLite queue data and is independent of host dependency readiness.
- Validate each feed independently. Require the expected project ID and a complete, fresh database observation for queue counts. Host-dependency `unknown` status must not invalidate complete database counts. Missing, stale, malformed, or mismatched data stays unknown; never display zero as a fallback.
- Show source-specific failure reasons and check times. Distinguish a project mismatch from incomplete or stale data without exposing raw command output.
- Coalesce overlapping refreshes for the same workspace and settings. After three identical failures, pause automatic retries; opening the dashboard, an explicit refresh, or a workspace/profile-setting change makes one fresh attempt.
- Select the Hermes profile from an owner-managed, application-scoped map keyed by the exact project ID returned by Curator. Keep the Curator profile routing setting separate from Hermes profile selection.
- Write generated inbox and SDE queue files only when their actual contents change. Keep the last-check time in the dashboard so it can update without rewriting unchanged files.

## Tests and acceptance

- Cover each feed succeeding or failing independently, including project mismatch, stale and incomplete responses, and complete queue data when Hermes readiness is unknown.
- Verify repeated identical queue snapshots leave generated files unchanged, overlapping refresh triggers don’t launch duplicate reads, and three identical failures pause automatic retries.
- Run the focused extension checks and inspect the reloaded dashboard: health must reflect Hermes, queues must match Curator’s project-scoped counts, and each panel must show its own failure state.

## Assumptions

- Keep the change within Curator V2. Add a read-only `project_queue_snapshot` MCP tool because `project_health` combines database counts with host readiness and cannot meet the independent-feed contract on its own.
- Use the recommended feed split and three-identical-failure retry pause. Bind Hermes profiles, SQLite databases, and host evidence files by exact project ID in VS Code User settings; retain the existing single-project paths as fallbacks. Do not change project files or initialize databases.
- Preserve existing worktree changes. Keep the repair within the V2 backend and extension. The queue snapshot is a read model and does not change the database schema or service state.
